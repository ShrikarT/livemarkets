# V3

V2 made the product real: a live book, two clocks, a stream layer, onboarding, and
an app you can trade from. V3 is the layer on top -- the things that make a round
worth coming back to, and the controls that make running it survivable.

Everything here is UI and service code. **No new Solidity was written for V3**,
because the primitives it needs were already in `Market.sol`: `Claimed`,
`CrankRewardPaid`, `setTradingPaused`, `tradingPaused`, and `claimAndWithdraw`.
That is worth stating plainly, since "V3" could easily be read as another contract
rewrite that would need another audit pass.

## What shipped

| Surface | Route / module | The idea |
| --- | --- | --- |
| Leaderboard | `/app/leaderboard`, `lib/leaderboard.ts` | Winnings read from chain logs, not a counter |
| Shareable result | `/r/[address]`, `/api/og/result/[address]` | A URL, not a share button |
| Settlement truth | `lib/settlement.ts` | One wei-exact source for what a position is worth |
| Portfolio | `/app/portfolio` | Quoted in MON after fees, with realised P&L |

## The leaderboard is not a counter

It is built from `Claimed` and `CrankRewardPaid` logs over a block window. Nothing
writes to it, so there is no endpoint to forge and no row anyone can inject with
`curl`.

Two limits it states about itself, on the page:

- It shows **winnings, not profit**. It sums what people took out, not what they
  put in. Someone who staked 40 MON to win 10 ranks above someone who staked 1 to
  win 9, which is not what "winning" usually means.
- It covers a **block window** (`LOOKBACK_BLOCKS`, roughly two hours at 400ms
  blocks), not all time. A leaderboard that silently means "recently" is a
  leaderboard that lies slowly.

A number that describes its own limits is more useful than a bigger number that
does not.

## A result you can paste into a group chat

`/r/[address]?who=0x...` renders a settled round with an OG image, so the artefact
you share is a **link that keeps working** rather than a screenshot that rots.

Two decisions worth keeping:

- **Losses render in the same typography as wins.** A product that makes winning
  loud and losing quiet is teaching people to misremember their own record.
- The image is cached `immutable` only once the badge says `SETTLED`. Before that
  it is `max-age=5`, because a cached picture of a market that has since resolved
  is worse than a slow one.

## One place that knows what a position is worth

`lib/settlement.ts` folds each tick through `netPayout` from `market-math.ts`, so
fees are applied **per tick** rather than once on a total. That is not a
refactor-for-tidiness: applying a fee to a summed total gives a different number
than applying it per tick, and the contract does it per tick.

The share card, the result page, and the portfolio all read from it. Before this
existed the portfolio did its own arithmetic and got a real thing wrong -- it
computed staked cost with a rounding-down divide while every collateral debit in
`Market.sol` rounds **up** (`mulDivUp`), so it quietly understated what you paid.

## The kill switch

Pausing was wired to the contract but had three bugs that together made it
useless. All three are worth naming, because each one looks fine in review:

1. **The button only ever sent `true`.** The handler took a boolean and the toast
   already said "Trading resumed", but no caller could send `false`. A stop you
   cannot un-pull is a foot-gun, not a safety feature.
2. **Nothing read `tradingPaused()`.** The only way to find out whether a market
   was already stopped was to try stopping it.
3. **It was unreachable when it mattered.** The button rendered only inside a list
   filtered to `phase !== Open` -- so it did not exist during the one phase in
   which trading happens.

It now polls real paused state, toggles against it, and is present for every
unsettled market you control. While the state is unread the row says `state
unread` rather than `live`, because unknown is not the same as safe.

The friction is deliberately asymmetric: **resolving** needs the outcome typed out
in full because it is irreversible, while **pausing** is one click because it is
reversible and a confirmation dialog in front of an emergency stop is how the stop
arrives too late.

It also makes *fewer* RPC calls than before. `resolver()` is set in the
constructor and cannot change, yet it was re-read for all 24 scanned markets every
two seconds. It is now read once per market and cached.

## Referrals

The easy version is an endpoint that takes `{ referrer, referred }` and bumps a
counter. That is forgeable in one line of `curl`: script a POST claiming credit
for every address that has ever traded, and whoever posts first wins.

So the **referred** address signs the attribution. Only the person who was
actually referred can credit their referrer.

- Verification goes through `publicClient.verifyMessage`, not viem's standalone
  helper, because the client action also validates **ERC-1271 smart-contract
  account** signatures. This app is passkey-first via Privy embedded wallets, so a
  large share of users will not have a plain EOA and the standalone helper would
  reject perfectly valid signatures.
- **The code is just an address.** A short random code needs a stored
  `code -> address` map, which breaks when KV is unconfigured and brings
  collisions and expiry with it. `?ref=0x...` needs no storage to issue.
- **First link wins.** A later `?ref=` never overwrites an earlier one, otherwise
  the last person to send you a link steals credit from whoever introduced you.
- The signed text is shown in full before you sign it, names both parties so it
  cannot be replayed for a different referrer, and says that no funds move.
  "Sign this opaque hex" is the shape of a phishing prompt.
- Guards run cheapest-first: self-referral, then per-IP daily rate limit on hashed
  IPs, then the signature, then `addOnce()` for one attribution per address ever.
  There is no point spending an RPC call verifying a signature for an address that
  has already been credited.

Responses carry `persisted`. When KV is not configured the panel says counts reset
on restart instead of implying durability.

## Deliberately not built

**The house maker bot.** `config/contracts.ts` already carries its parameters
(`spreadBps`, `sizePerLegWei`, `maxExposurePerRoundWei`, `maxDailyLossWei`), so it
looks like a small job. It is not, and the reason is not effort: it is a service
that holds a funded private key and places orders unattended. Nothing in this
repo has been executed yet -- no `npm run build`, no `forge test` -- and shipping
an untested process whose failure mode is *losing money while nobody is watching*
is not a trade worth making for a demo. It wants a dry-run mode and a real
exposure test before it touches a key.

**Crank reward claiming in the UI.** `payCrankReward(tick)` exists on chain and
`MarketRoom` already cranks with `matchTick(tick, 64)`, so cranking works and
rewards accrue. Only the claim button is missing.

Both are listed here rather than left as silent gaps, because a roadmap that
quietly drops items is how a project loses track of what it decided.

## Verification status

Same rule as the root README: this table says what was checked, not what passed a
build.

| Thing | State |
| --- | --- |
| Types across V3 files | Checked with `tsc --strict` against declared stubs |
| Cost / payout parity | Folded through `market-math.ts`, which is parity-tested |
| `next build` | **Not run.** No network in the authoring sandbox |
| `forge build` / `forge test` | **Not run.** No Foundry in the authoring sandbox |
| Signature verification path | Verified against current viem docs, not executed |

The honest summary: the arithmetic is checked and the types are checked, and
nothing has been compiled or deployed. Run `npm i && npm run build` and
`forge test` before you trust any of it.
